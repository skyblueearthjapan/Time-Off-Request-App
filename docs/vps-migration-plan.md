## 1. 結論

- 今の GAS 版（本番 @106）を、機能・画面・帳票・癖を変えずに VPS（FastAPI＋PostgreSQL＋worker＋Cloudflare Tunnel）へ移します。構成と決定 A〜D は残業と同じです（K-0）。新しいアドレスは `https://leave.lineworks-local.net` です（K-1）。
- 業務データの正は VPS の DB です。今のスプレッドシートの `T_LEAVE_REQUEST` には、**VPS が書くたびに該当の行だけを数秒〜1 分で反映します**（決定 A）。行の位置・日付の型・表示形式を保ち、行もタブも消しません。統合業務メール（7:00・17:00・18:00）と、戻した GAS が今と同じシートを読んで動き続けます。
- 集計タブ `V_LEAVE_SUMMARY` は、VPS が DB から今と同じ 12 列・同じ並びで書き直します（ディレクター判断）。統合業務メールが「警告レベル」などを読むためです。
- **PDF・サイン画像・台帳・承認完了メールは、今の GAS の関数をそのまま使います**（決定 B、K-5）。VPS の worker が行を反映した後で、GAS の内部用の入口を 1 件ずつ呼びます。見た目・中身・順序・宛先が今と同じになります。
- 日付の計算はすべて日本時間です（決定 C）。マスタ同期（作業員・カレンダー・電子印・部署承認者）は VPS が今と同じ規則で行い、DB の同じタブにも今の形で書きます（決定 D）。
- **このアプリ特有の山は 2 つです。** ① GAS の Web アプリが `access: DOMAIN` なので、残業のように token だけで内部用の入口を呼べません。呼び方はステージングのスパイクで決めます（4-5）。② 本番の `T_LEAVE_REQUEST` には `PDF_FILE_ID` の列が無く、今の GAS は前の PDF をゴミ箱へ移していません（確認済み・コード×実物の見出し）。この動きもそのまま再現します（4-6）。
- 直すと決めたものは、1 次承認の状態の確かめ・二重承認・二重押し（K-4）、2 次承認のやり直しの穴、XSS、スマホ向けの配置（K-7）、存在しない申請番号での待ち、保守の関数を管理者だけに（オーナーに確認中）、です（3-3）。ほかの癖は既定で「今のまま」です。
- Sebastian はこのアプリのシートに書いていません（確認済み）。残業にあった `sheet_intake`・転送役は作りません。旧フォーム・朝バッチもありません。
- 進行中の案件は、申請中 1 件・2 次承認待ち 0 件です（2026-11-26 午前。切り替えの直前に数え直します）。状態のまま移せば VPS で続けられ、送り直すメールはありません。
- 切り替えは両方のデプロイ（@106・@104）に移転モードを当てます（K-2）。統合業務メールの時刻とマスタ同期（6 時台）を避けた時間に行います。日時はオーナーが決めます（未決。9-2 Q1）。
- 戻しは「VPS を止めて GAS の移転モードを外す」が中心です（シートが常に最新のため。6-6）。
- 工数の見込みは作業 9〜13 時間（作業日で 1.5〜2 日）＋見守り 5 営業日です（推測。7 章）。

### 3-2. 今のまま移す癖（K-0「社員を信頼する作り」と「機能を落とさない」から）

- 申請・プレビュー・1 次承認（サイン）・編集・取消・取得状況を、ドメインの誰でもできます。電子印は誰の印でも選べます（要件定義「承認者の特定は不要」）。
- 編集は保存するだけで承認が外れます（変更が無くても。2 次承認済みも外れる）。
- 取消は承認済・2 次承認済みでもできます。承認日時・承認者の列は残ります。
- 申請で見ないもの: 区分・種類の値、半日の振替休暇、振替元が休日か・未来か、同じ人・同じ日の重複、マスタにあるか。編集では休暇日が勤務日か・年度内かを見ません。
- 申請の入力が残って送られる（半日→午前を選んでから全日に戻すと `午前` のまま、種類を変えても振替元・理由が残る）[inv-2 D-6]。
- 年度は行の値を使い、計算し直しません。3/11 より前の行には 4/1 区切りの年度が残ります [inv-4 0 節 #4]。
- 数え方の違い（半日の有給は集計 0.5・期間別と台帳 1、年度の決め方、期限 12/31 と期間 11/30、「過ぎた」の比べ方 3 通り）。
- 理由の既定の字が場所で違う（確認画面「私用のため」、プレビュー・台帳「私用の為」）。時間帯の「～」も PDF と台帳で字が違います。
- 台帳の「1次承認者」はメール、「2次承認者」は名前。累計は書いた時点の値で、後から直りません。
- 古い管理画面（`?page=admin`）は承認済みが 0 件の人を出しません。取得状況の予定は部署を移る前の申請を出しません。
- 2 次承認待ち一覧に半日区分が出ません。プレビューの過去申請バッジは一度も出ません（返り値に項目が無い）。
- 総務管理・部署管理・古い管理画面は、年度を変えても読み直しません（「更新」が要る）。
- 一括 2 次承認は戻り値の `ok` を見ずに成功として数えます。
- サインは画面の大きさが変わると消えます [inv-2 §9]。
- 作業員の自動選択は働きません（作業員マスタに Google アカウントの列が無い）。
- 本番では前の PDF をゴミ箱へ移さず、編集・取消で PDF の URL も空にしません（`PDF_FILE_ID` の列が無いため。4-6）。
- 作業員マスタの上限は無し（残業の 80 人のような切り方はしない）。

### 3-4. ディレクターの提案（了承待ち。9-2 の質問に載せる）

- 承認待ち一覧の並び順を、年を入れて並べる（表示は `MM/dd HH:mm` のまま）。今は文字の比べ方なので、年をまたぐと 12 月の申請が 1 月より上に出ます [inv-1 M9]（9-2 Q3）。
- PDF・台帳・承認完了メールの GAS の仕事が失敗したら再試行する（今は 1 回だけ試して黙って続ける）（9-2 Q6）。
- 有給警告メールの手動送信（メニュー）は移さない。統合業務メールが同じ役目を担っています（9-2 Q8）。
- iframe への埋め込みは自分のサイトだけに限る（`frame-ancestors 'self'`）。ポータルは `same_tab` で開くので埋め込んでいません（確認済み・APP_MASTER）。ほかの埋め込みは見つかっていません（推測）。
- 画面を開いても集計タブを書き直さない（画面は DB から計算します。表示は同じ）。同時に開いたときに集計タブが一瞬空になる問題 [inv-1 S6] が消えます。利用者から見える差はありません。

### 4-1. 全体の形（決定 A〜D を当てはめた。名前と細部は提案）

残業と同じ 6 コンテナです（K-0）。名前・ボリューム・ネットワークはすべて `kyuka-` で始め、ホストにポートを出しません。これに加えて、**今の GAS（DB に紐づいたプロジェクト）を「PDF・サイン画像・台帳・承認完了メールの係」として残します**（決定 B）。

| 部品 | 役目 | 写す元 |
|---|---|---|
| `kyuka-db` | PostgreSQL 16。ボリューム `kyuka-pgdata` | 残業 compose |
| `kyuka-api` | FastAPI。ページの HTML（入口の判定とテンプレート変数）、`/api/rpc/{関数名}`、`/auth/*`、`/healthz`。書き込みは DB の取引の中で、行の反映・集計タブ・GAS の仕事を outbox（`jobs`）に積む | 残業 `vps-app/api` |
| `kyuka-worker` | 同じイメージで `python -m app.worker`。レーンは ①行の反映（`sheet_row_sync`）②集計タブの書き直し（`summary_rewrite`）③GAS の内部用の入口（`gas_call`、全体で 1 本ずつ）④定期処理（4-9） | 残業 `jobs.py`・`worker.py`。②は新しく作る |
| `kyuka-web` | nginx。ページの JS・CSS と `/api/`・`/auth/`・`/healthz` の中継。本文の上限はサイン画像のため 1MB 以上 | 残業 `web/nginx.conf` |
| `kyuka-cloudflared` | Tunnel `leave-vps`。転送先 `http://web:80` | 残業 `cloudflare/` |
| `kyuka-backup` | 毎日 3 時に `pg_dump -Fc`、1KB 未満は FAILED | 残業 `backup/` |
| **今の GAS**（`15aGUL5i…`） | 切り替えた後は、内部用の入口（4-6a）だけが動く。画面・トリガーは移転モードで止める（6-3） | 今のコードに `Internal.gs`・`Cutover.gs`（残業の型）と `doPost` を足す |

データの流れ（2 次承認の例）:

1. 総務が 2 次承認を押します。api は DB の申請の行をロックし、状態と `expectedStatus` を照合して 3 列（2 次承認者名・メール・日時）を書きます。同じ取引で、行の反映・集計タブ・GAS の仕事（`internal.afterApprove2`）を積み、画面へすぐ返します。
2. worker のレーン①が、その行をシートの同じ位置に書きます（数秒〜1 分。5-5）。
3. レーン③が、行の反映の待ちが 0 であることを確かめてから GAS の入口を呼びます。GAS は今の関数で PDF と台帳を作り、PDF の列をシートに書き、結果を返します。
4. VPS は返ってきた `pdfUrl` などを DB に入れます。シートと同じ値なので、レーン①は書き直しません。

Google の API は、GAS の持ち主（オーナー）の委任トークンで呼びます。VPS が使うのは Sheets（DB の行の反映・集計タブ・マスタ元と残業 DB の読み取り・マスタ 4 タブの書き込み）と、切り替えの控えを作る道具の Drive（読み取りと複製）だけです。PDF・サイン・台帳・メールは GAS が扱うので、VPS は Drive に書かず、Gmail のスコープも持ちません。スコープは最初に決めます（後から足すと許可のやり直しが要る＝罠 7）。内部用の入口を第 1 案（4-5）で呼ぶなら、そのためのスコープ（Drive を含む見込み）も最初に入れます。

- 各行に `sheet_row`（シートの行番号）を持ちます。移行で元の行番号を入れ、VPS で足した行は書いた位置を入れます。

- 行ロック: 申請 1 件ごとの `SELECT … FOR UPDATE`。REQ_ID は（申請日, 連番）に一意制約をかけて取引の中で採番します。連番は**シートに残る全行**（移さなかった行も）を数に入れます [inv-4 §7]。
- 並べ方は、JS の既定の `sort()`・`localeCompare()`・`localeCompare(…,'ja')` の 3 種類を関数ごとに再現します [inv-1 §10]。

### 5-5. シートへの行単位の反映（決定 A）

残業の `row_sync.py` を写し、`T_LEAVE_REQUEST` の 1 タブに当てます。

- api は DB の取引の中で、変えた行ごとに仕事を積みます。worker は DB の**今の**値を読み、変わった列（V 区分）だけを書きます。G 区分の列（サイン・PDF）と N 区分の列は書きません。
- 行の位置: 今ある行は `sheet_row` の位置に書きます。書く前に、その行の REQ_ID を読んで DB の値と同じかを確かめ、違えば REQ_ID の列を全部読んで探し直します。見つからなければ書かずに止め、管理者に知らせます。新しい行は最後のデータ行の次に足します（GAS と同じ）。
- 行・列・タブの削除・挿入・並べ替えはしません。取消も今と同じく状態の書き換えです。
- 型: 段階 2 で全列を `UNFORMATTED_VALUE` で読み、列ごと（混ざる列は行ごと）の型と表示形式の表を作ります。
  - 日付・日時のセルの列（`APPLIED_AT`・`APPROVED_AT`・`APPROVED_AT2`・`LEAVE_DATE`・`SUBSTITUTE_FOR_WORK_DATE`）: **DB のファイルの時間帯の壁時計**でシリアル値を作り、RAW で書き、同じ列の表示形式を当てます。休暇日・振替元は JST の 0 時、ほかはその時刻です。統合業務メールは休暇日が Date 型でない行を飛ばすので、ここを外すと通知から申請が消えます。
  - 文字の列（理由・氏名など）: RAW で書きます。GAS の `setValues` は `=` で始まる値を数式に、`1/2` のような文字を日付に変えていましたが、VPS は文字のまま書きます（受け入れる差。変える／変えない一覧に載せる）。
  - 作業員 ID・年度: 型の表で決めます（今の行が数なら数で書く）。
  - 空は空のまま書きます（`APPROVED_AT2` は空かどうかで 2 次承認待ちが決まる）。
- 受け入れ条件: ステージングで、VPS が足した行・書き換えた行を GAS の `api_getLeaveRequestById` と統合業務メールの読み方で読み、日時の列が `Date` で返り、日付が JST で正しいこと。
- 毎晩の照合（`sheet_reconcile`、2 時台）: 全行を UNFORMATTED と FORMATTED で読み、DB と 1 セルずつ比べ、差があれば DB の値で書き直して記録します。シートにあって DB に無い行は消さずに報告します。DB の行が 0 件、またはシートより少ないときは 1 行も書かずに止めます（罠 49）。書かずに数えるだけの `--check` も持ちます。
- 運用: 「`T_LEAVE_REQUEST` を手で直しても、次の書き込みか毎晩の照合で DB の値に戻る」ことを管理者に伝えます。

### 5-6. リハーサル

- ステージングで本番からの移行を 2 回以上行い、数字を控えて当日の dry-run と比べます。
- 移行の直後に照合を `--check` で流し、差 0（移した値を書き戻しても型・表示形式・位置が変わらない）を確かめます。
- 画面からの操作（申請・1 次承認の電子印と手書き・2 次承認 1 件と一括 3 件・編集・取消・過去申請・振替休暇）の後、行が 1 分以内にシートに出て、5-5 の型の条件を満たすこと。集計タブが書き直されること。
- 写しの GAS で、サイン画像・PDF・台帳・承認完了メール（オーナーにだけ届く）ができること。写しの GAS を止めて操作し、再試行と管理者の欄の表示を確かめること。
- 戻しの練習: VPS を止め、写しの GAS の移転モードを外し、画面・集計・PDF・台帳が今と同じに動くこと。

3. **C-3** GAS で `exitMigrationMode` → `restoreTriggersAfterRollback`（`syncAllMasters` 1 本。通知・警告のトリガーは作らない）。
4. **C-4** `syncAllMasters` と、メニューの集計の作り直しを手で 1 回動かす（GAS が今の形で書けることを確かめる）。
5. **C-5** C-2 で控えた仕事を GAS で手で処理する（2 次承認の PDF の作り直しは画面からできないので、`generateLeavePdf_` を呼ぶ管理の関数をエディタから。台帳は `updateLedger_`）。
6. **C-6** 本番 `/exec`（@106）で一覧が出て、VPS で最後に作られた申請が見えること。
7. **C-7** ポータルの url 列を @106 の `/exec` に戻す。Settings の `APP_URL` は変えていないので何もしない。
8. 利用者への案内はオーナーと相談します。

- 戻した後は VPS の DB を使いません。もう一度切り替えるときは移行からやり直します。
- 型と表示形式を保つので、戻した後に日時の見え方が変わる行は出ない見込みです（リハーサルの戻しの練習で確かめる）。
